03Problem
Where we look

Every code benchmark you know asks one question: does it run?

HumanEval, MBPP, SWE-bench. Generate, execute, count the passes. pass@1.

That question needs a harness, a test suite, and a definition of correct. It says nothing about the code you will be reading six months from now.

So how would you measure whether generated code is any good — without running it? Thirty seconds. What would you compute, and what would you compare it against?

04Benchmark
Why another benchmark

Correctness is not quality.

BenchmarkAsksNeeds
HumanEval · MBPPdoes the function pass its unit tests?a test harness
SWE-benchdoes the patch turn the repo's suite green?repo + env + tests
CQBenchis the code substantial, defect-free, weakness-free?a parser + 2 analyzers

A function can pass every test it is given and still shell out through os.system, swallow the exception, and never close the socket. That code is correct. It is not good.

06Example
What a task actually looks like

One task. Two answers. One verdict each.

task def evaluate(self, task, expression) spec “Evaluate the given expression in the context of the given task.”
Human — the original
def evaluate(self, task, expression): if isinstance(expression, Operator): return expression._matches(task) else: return self._eval(task, expression, **task.data)

clean_strict@1 ✓   0 defects · 0 weaknesses

Claude Opus 4.8 — under test
def evaluate(self, task, expression): """Evaluate the given expression …""" context = self.get_context(task) \ if hasattr(self, "get_context") else {} return eval(expression, {"__builtins__": {}}, dict(context))

clean_strict@1 ✗   eval-used · CWE-95

Both clear every structural check. The score turns on two named things — and the model reached for eval where the human reached for a method the codebase already had.

07Construction
How the tasks were chosen

A task is here because models already failed it.

~256,000 candidate Python functions in  →  10,354 tasks out. These three did the filtering.

ChatGPT · general purpose

gpt-3.5-turbo · 2023

DeepSeek-Coder · code, open

33B-Instruct · 2024

Qwen2.5-Coder · code, open

32B-Instruct · 2024

Every candidate went to all three. A task was kept only when two of the three produced three or more findings each, and those findings fell in the same class — the same ODC defect type, or the same CWE.

That last condition is the whole idea: it does not select hard tasks, it selects tasks where independent models fail the same way, so the failure is a property of the problem rather than of one model. All 10,354 cleared it; the 200 are a sample.

That is what quality means here, made countable: a set of named failure classes that two independent models walked into together.

09Scope
Scope

Nothing is executed.

What it measures

  • Did you write the function that was asked for?
  • Is it substantial, or a gesture?
  • What defects does a linter find, by type?
  • What weaknesses does a SAST tool find, by class and severity?

What it does not

  • Functional correctness — nothing is run against tests
  • Semantic equivalence to the original
  • Actual exploitability of a flagged pattern

A perfectly clean output can be completely wrong. Say this out loud whenever you quote a number from a static benchmark.

10Pipeline
The measurement

Four layers. Every one can veto.

01Is it the requested function, and more than a stub?ast
02Is it ≥10% of the human implementation's size?lizard
03Defects, mapped to ODC categoriespylint
04Weaknesses, mapped to CWE classessemgrep

clean_strict@1  =  01 and 02 and zero defects and zero findings

One number, six conjoined conditions, and a taxonomy translation in the middle of it. These are also the layers that picked the tasks three slides ago: the entry gate ran 01 and 02 on the human original, and counted 03 and 04 on the three models. Notebook 01 takes the whole thing apart by hand.

11Reading
Read this before you read any result

Failures are enriched here by design.

You can say

“On tasks where 2023–24 models failed alike, model X still fails on Y%.”

You cannot say

“Model X writes defective code Y% of the time.”

The human references trip a defect on 62% of these tasks, and clear the structural gate on 100% — an entry requirement. Facts about the sampling frame, not about programmers.

The asymmetry that makes it testable

The three marked built it fail these tasks by definition — their rates are a ceiling, not an estimate. Which is why beating them is the weakest possible result, and reaching the human is the one that means something.
