02Problem
Where the field looks

Almost everything we measure about generated code, we measure in the first minute of its life.

Does it compile? Does it pass the tests? pass@1. HumanEval, MBPP, MultiPL-E, SWE-bench. Every one of them asks a question about the moment the code is written.

That moment is real, and it is not where software spends its money.

03Problem
Where the cost is

Code is written once and read, reviewed, patched and secured for years.

60–80% of lifecycle cost

falls after first authorship — maintenance and evolution, not writing.

Unfixed and accumulating

A large share of the smells and security issues introduced in AI-authored commits are never repaired; they persist as debt.

Invisible to the test suite

A missing timeout, an unvalidated path, a swallowed exception. All pass green.

The developer's job moved from authoring to reviewing. Our measurements didn't move with it.

04Problem
The question for today

So how would you measure whether generated code is any good — without running it?

Think about it concretely for thirty seconds. What would you compute? What would you compare it against? What would make your answer wrong?

06Benchmark
Scope

Nothing is executed.

What it measures

  • Did you write the function that was asked for?
  • Is it substantial, or a gesture?
  • What defects does a linter find, by type?
  • What weaknesses does a SAST tool find, by class and severity?

What it does not

  • Functional correctness — nothing is run against tests
  • Semantic equivalence to the original
  • Actual exploitability of a flagged pattern

A perfectly clean output can be completely wrong. Say this out loud whenever you quote a number from a static benchmark.

08Pipeline
The instruments

Two tools, two different questions.

pylint — a linter

Reads Python without running it. Reports what is wrong, suspicious, or unmaintainable.

  • unspecified-encoding — a file opened without an encoding; breaks on someone else's machine
  • missing-timeout — an HTTP call that can hang forever
  • unused-variable — a value computed and never read

semgrep — a SAST tool

Matches code against rules describing shapes that create risk.

  • B602 — a shell command built with shell=True
  • B410 — XML parsed by a library that resolves external entities
  • B113 — a request with no timeout

Not one of these fails a test suite. That is the entire argument for measuring code this way — and also the reason to be careful: semgrep reports a pattern, never a proven exploit.

09Pipeline
The part everyone skips

A count of linter warnings is not a scientific quantity.

It depends on which checks that tool implements this year, and cannot be compared with a Java or C analyzer. So findings are translated first.

ODCOrthogonal Defect Classification — classifies a defect by the kind of fix it needs: Assignment · Checking · Algorithm · Interface · Function/Class/Object · TimingIBM, 1992
CWECommon Weakness Enumeration — the industry catalogue of weakness types: CWE-78 command injection, CWE-611 XXE, CWE-400 resource exhaustionMITRE

The mappings do double duty: they translate, and they filter. A finding with no category is not counted at all — so the spreadsheet defining them is part of the benchmark.

11Sampling
Read this before you read any result

These tasks were kept because models failed them.

Out of ~256,000 Python candidates, a task survives only if two models cleared a 10% complexity floor, each produced ≥3 findings, and those findings shared a defect type or weakness class. Not hard tasks — tasks where independent models fail the same way.

You can say

“On tasks where 2023–24 models failed alike, model X still fails on Y%.”

You cannot say

“Model X writes defective code Y% of the time.”

The human references trip a defect on 62% of these tasks, and clear the structural gate on 100% — an entry requirement. Facts about the sampling frame, not about programmers.

16Today
The three questions

What we're actually asking.

RQ1Do models write structurally different code from humans?complexity · lexis
RQ2Do they make different kinds of mistake?odc
RQ3Do they introduce different weaknesses, at different severity?cwe

Same 200 tasks for every author, so every comparison is paired — we compare answers to the same question, not two populations. That turns out to matter more than any other choice in the pipeline.

17Point
What you're really practising

Anyone can run a benchmark. The skill is knowing which of its numbers you would defend.

  • A metric that collapses can be measuring instruction-following, not quality.
  • A defect can be inherited from the task, or manufactured by the evaluation format.
  • An average can reverse depending on how you aggregate it.
  • A headline difference can rest on one permissive rule — or survive losing it.
  • And a pipeline can reproduce perfectly — until it meets a dependency nobody pinned.

Every one of those is in today's data. You'll find them yourself.
